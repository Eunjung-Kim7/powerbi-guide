데이터 정제·변환·결합 · 3~7주차
▶
📖 핵심 용어 정의
파워쿼리 편집기
데이터를 시각화 전에 정제·변환하는 ETL 도구. 모든 작업이 적용된 단계(Applied Steps)로 기록 → 언제든 수정·삭제 가능. M 언어 기반.
적용된 단계 (Applied Steps)
오른쪽 패널에 변환 작업이 순서대로 쌓임. 단계 클릭 → 그 시점 데이터 상태 확인 가능. 잘못된 단계는 X 클릭으로 삭제.
피벗 (Pivot)
행 값을 열로 펼치기. 연도가 행으로 나열된 데이터를 연도별 열로 변환할 때 사용.
예) 연도 행 → 2022열·2023열·2024열
언피벗 (Unpivot)
여러 열을 하나의 행으로 쌓기. 공공데이터의 연도별 열 구조를 Power BI에 맞는 행 구조로 변환할 때 필수.
예) 2022열·2023열 → 연도·값 두 열
추가 (Append)
같은 구조 테이블을 세로로 합치기 (SQL UNION).
예) 2023년 판매 + 2024년 판매 → 전체 판매
병합 (Merge)
공통 키로 두 테이블을 가로로 합치기 (SQL JOIN). 왼쪽 외부·내부·완전 외부 조인 지원.
예) 판매 + 고객 테이블 → 고객ID로 병합
null
값이 없음을 나타내는 특수값. 빈 셀과 다름. 처리법: 변환 → 채우기(아래) / 홈 → 행 제거 → 오류 행 제거 / 값 바꾸기
데이터 형식
반드시 정확히 설정. DAX 함수·관계·날짜 인텔리전스 정상 작동 조건.

🗂️ 데이터 모델이란? — "엑셀 VLOOKUP을 자동화한 것"
엑셀에서 두 시트를 연결할 때 VLOOKUP을 쓰죠? Power BI의 데이터 모델은 그 연결을 한 번만 설정해두면 이후에는 자동으로 작동하는 구조입니다.
예) 세대 테이블과 자치구 테이블을 "자치구명"으로 연결 → 이후 시각화에서 두 테이블 데이터를 자유롭게 함께 사용 가능.

관계 설정하는 방법
Model 뷰(왼쪽 세 번째 아이콘) 클릭 →

기본 키(PK) vs 외래 키(FK)
기본 키(PK): 중복 없는 고유값 열. 예) 자치구 테이블의 "자치구코드"
외래 키(FK): 다른 테이블을 참조하는 열. 예) 세대 테이블의 "자치구코드"

👉 PK 쪽이 "1", FK 쪽이 "다(N)" — 항상 1:N 방향으로 연결
1:N 관계란? — 비유로 이해하기
자치구 테이블 (1쪽): 강남구, 관악구, 마포구… → 각 이름이 딱 1번씩만 나옴
세대 테이블 (N쪽): 강남구 2020년, 강남구 2021년… → 같은 자치구가 여러 번 나옴

👉 "1"인 테이블(자치구)로 "N"인 테이블(세대)을 필터링하는 방향이 기본
⚙️ 관계 속성 — 관계 선을 더블클릭하면 보이는 설정들
속성 쉬운 설명 & 언제 쓰나
활성 관계
실선		기본으로 사용되는 관계. 두 테이블 사이에 실선으로 표시. 자동으로 필터가 전달됨. 대부분의 경우 이것 하나만 쓰면 됨
비활성 관계
점선		같은 테이블 사이에 두 번째 관계를 만들 때 자동으로 비활성화됨(점선). DAX에서 USERELATIONSHIP()으로만 사용 가능
필터 방향
단방향		기본값. 권장. 1→N 방향으로만 필터 전달. 예) 자치구 필터 → 세대 데이터 필터링. 반대 방향은 자동으로 안 됨
필터 방향
양방향		양쪽 모두 필터 전달. 복잡한 모델에서는 의도치 않은 필터 전파로 오류 발생 가능 → 꼭 필요한 경우에만 사용
카디널리티관계의 종류. 1:N(가장 일반적) / 1:1(같은 키가 양쪽에 딱 하나씩) / N:N(중간 브릿지 테이블 필요, 고급)
🔑 다중 키 — 두 열 이상으로 연결해야 할 때
다중 키란?
Power BI 관계는 열 하나로만 연결 가능합니다. 하지만 실무에서는 "자치구+연도" 조합으로만 유일한 경우가 있어요.

예) 세대 테이블에서 강남구-2023이 유일한 행 → "자치구코드"만으로는 중복 발생
해결 방법 — 복합 키 열 만들기
파워쿼리 또는 계산 열로 두 값을 합친 새 열 생성 후 그 열로 관계 연결:

파워쿼리: 열 추가 → 사용자 지정 열
[자치구코드] & "_" & Text.From([연도])

계산 열(DAX):
복합키 = [자치구코드] & "_" & FORMAT([연도],"0")
📋 계산 열 (Calculated Column) — "테이블에 새 열 추가"
언제 씁니까?

🔢 숫자 범주화 (Binning) — 연속 숫자를 구간으로 분류
💡 Bin이란?
Bin은 영어로 "통, 상자, 구간"이라는 뜻입니다. 데이터 분석에서는 연속적인 숫자를 일정 간격의 구간(통)으로 나눠 담는 것을 의미합니다.

예를 들어 1인 세대 수가 3,200 / 7,800 / 14,500 / 22,000 처럼 다양한 숫자로 흩어져 있을 때,
→ "0~5000", "5000~10000", "10000~20000", "20000 이상" 구간(Bin)으로 나누면
→ 분포 패턴을 한눈에 파악할 수 있게 됩니다.

히스토그램 차트의 각 막대 하나가 바로 Bin 하나입니다.
연속적인 숫자 데이터(세대 수, 비율 등)를 일정 구간(Bin)으로 나눠 분포를 파악하거나 히스토그램을 만들 때 사용합니다.

4

-- 1인세대 수를 구간으로 분류 세대수구간 = SWITCH(TRUE(), 세대[1인세대수] < 5000, "①5천 미만", 세대[1인세대수] < 10000, "②5천~1만", 세대[1인세대수] < 20000, "③1만~2만", "④2만 이상" )
앞에 ①②③④ 번호를 붙이면
슬라이서에서 순서대로 정렬됨
💡 그룹 기능 vs 계산 열: 그룹(Bin)은 구간 크기가 일정할 때 빠르게 사용. 계산 열(SWITCH)은 구간 경계를 직접 지정하거나 앞에 번호를 붙여 정렬 순서를 제어할 때 유리.
📅 날짜 테이블 — 시간 분석의 필수 준비물
왜 필요한가? TOTALYTD, SAMEPERIODLASTYEAR 같은 시간 인텔리전스 함수는 연속된 날짜 테이블이 있어야 작동합니다. 없으면 함수가 오류를 냅니다.

만드는 방법 (2가지):
① 자동 생성: 홈 탭 → 새 테이블 → 날짜테이블 = CALENDARAUTO() → 데이터의 최소·최대 날짜 기준 자동 생성
② 범위 지정: 날짜테이블 = CALENDAR(DATE(2019,1,1), DATE(2024,12,31))

생성 후 반드시: 날짜 테이블의 날짜 열 선택 → 테이블 도구 탭 → 날짜 테이블로 표시 클릭

📖 데이터 분석이란? — 왜 배우는가
데이터 분석의 정의
원시 데이터(Raw Data)에서 의미 있는 패턴·인사이트를 찾아 의사결정에 활용하는 과정.

단순히 차트를 만드는 게 아니라 "왜 이런 일이 일어났는가"를 데이터로 설명하는 것.
데이터 분석 5단계 흐름
① 수집 — 공공데이터·업무 데이터 등 원천 확보
② 전처리 — 오류 제거, 형식 통일 (파워쿼리)
③ 모델링 — 테이블 간 관계 설정, DAX 수식
④ 시각화 — 차트·대시보드로 표현
⑤ 해석 — 인사이트 도출 및 보고

🗂️ 데이터 모델링이란? — 핵심 정의
데이터 모델링의 정의
여러 테이블 간의 관계를 설정하여 하나의 통합된 분석 공간을 만드는 작업.

엑셀 비유: VLOOKUP을 매번 수식으로 작성하는 대신, 테이블 연결을 한 번만 설정해두면 이후 모든 시각화에서 자동으로 활용 가능.

예) 매출 테이블 + 제품 테이블 + 지역 테이블을 연결 → 제품별·지역별 매출 분석을 수식 없이 바로 가능
모델링이 필요한 이유
하나의 테이블에 모든 데이터를 넣으면:
• 데이터 중복 → 파일 용량 증가
• 수정 시 여러 곳 변경 필요 → 오류 발생

테이블을 분리하고 관계로 연결하면:
• 중복 없이 깔끔한 구조
• 유지보수가 쉬움
• DAX 함수가 관계를 따라 자동 집계
스타 스키마 — Power BI 표준 구조
팩트 테이블 하나를 중심으로 여러 차원 테이블이 별(★)처럼 둘러싸는 구조.

팩트: 매출·세대수 등 수치 데이터
차원: 제품·자치구·날짜 등 분류 기준

🗂️ 팩트 테이블 vs 차원 테이블 — 모델의 두 축
📦 팩트 테이블 (Fact Table)
실제 측정값·수치 데이터가 담긴 테이블. 행이 많고 숫자 열이 많음.

포함되는 열:
• 차원 테이블을 참조하는 외래 키(FK) (자치구코드, 날짜 등)
• 집계할 수치 열 (1인세대수, 매출금액, 수량 등)

예) 매출 테이블: 주문일자·제품코드·지역코드·매출금액·수량
👉 "무엇을 얼마나" 에 해당하는 데이터
📋 차원 테이블 (Dimension Table)
분류·설명 기준이 되는 마스터 정보 테이블. 행이 적고 텍스트 열이 많음.

핵심 특징:
• 기본 키(PK) — 각 행을 유일하게 구분하는 열. 중복값이 절대 없어야 함
• 마스터 정보 — 코드에 대한 이름·속성·분류 등 상세 설명

예) 제품 테이블: 제품코드(PK)·제품명·카테고리·단가
예) 자치구 테이블: 자치구코드(PK)·자치구명·권역·면적
👉 "어디서·무엇이·어떤" 에 해당하는 데이터
🔑 기본 키(PK) vs 외래 키(FK)
기본 키(Primary Key)
차원 테이블에서 각 행을 유일하게 식별하는 열
조건: 중복 없음 + null 없음
예) 자치구코드: 110, 120, 130… (각 1개씩)

외래 키(Foreign Key)
팩트 테이블에서 차원 테이블의 PK를 참조하는 열
같은 값이 여러 번 나올 수 있음(중복 허용)
예) 세대 테이블의 자치구코드: 110, 110, 120… (반복)
⚠️ 참조 무결성
팩트 테이블의 FK 값이 차원 테이블의 PK에 반드시 존재해야 함.

문제 발생 예시:
세대 테이블에 자치구코드 "999"가 있는데 자치구 테이블에는 없음 → 관계 설정 시 오류 또는 빈 값 발생

해결: 파워쿼리에서 FK 열의 null·오타 제거 후 관계 설정
스타 스키마 구조
차원 테이블들이 팩트 테이블을 별(★)처럼 둘러싸는 구조.
Power BI 권장 표준 모델.

팩트(매출) ←── 제품 차원(PK: 제품코드)
팩트(매출) ←── 날짜 차원(PK: 날짜)
팩트(매출) ←── 지역 차원(PK: 지역코드)

화살표 방향 = 필터가 흐르는 방향 (차원→팩트)

언제 이런 상황이 생기나?
예) 매출 테이블에 날짜 열이 두 개 — "주문일자"와 "배송일자"
날짜 테이블과 두 열을 각각 연결하면 관계가 2개 생성
→ Power BI가 하나만 활성으로 유지, 나머지는 점선 처리

"이 관계를 활성으로 만들기" 체크박스:
관계 편집 창에서 어떤 관계를 기본 활성으로 쓸지 지정.
체크된 관계 = 실선 (기본으로 모든 시각화에 적용)
체크 해제된 관계 = 점선 (기본으로 사용 안 됨)

비활성 관계를 DAX에서 임시로 쓰려면:
CALCULATE([총매출금액], USERELATIONSHIP(매출[배송일자], 날짜[Date]))
→ 이 측정값 안에서만 비활성 관계(배송일자)가 활성으로 작동
📦 실전 예시 — 판매일만 연결했을 때 배송일은?
❌ 배송일은 자동으로 연동되지 않습니다
판매 테이블에 배송일 열이 있고, 날짜 테이블의 날짜와 데이터 형식이 같더라도
관계를 명시적으로 연결하지 않으면 Power BI는 배송일을 날짜 테이블과 전혀 연결하지 않습니다.

외래 키처럼 생겼어도 관계선을 직접 만들지 않으면 그냥 숫자/날짜 값이 있는 열일 뿐.
슬라이서로 날짜를 선택해도 배송일은 필터링되지 않습니다.
✅ 올바른 구성 방법
날짜 테이블[Date] ──실선──▶ 판매[판매일]  ← 활성 관계 (체크됨)
날짜 테이블[Date] ····점선···▶ 판매[배송일]  ← 비활성 관계 (체크 해제)

두 관계 모두 직접 만들어야 합니다.
판매일 관계를 먼저 만들면 → 자동으로 활성(실선)
배송일 관계를 추가로 만들면 → 자동으로 비활성(점선) 처리됨

이 상태에서:
• 슬라이서·차트 → 판매일 기준으로 자동 작동 (활성 관계)
• 배송일 기준 분석 → USERELATIONSHIP을 쓴 측정값으로만 가능
배송일 기준 측정값 만들기
-- 판매일 기준 (활성 관계 → 별도 설정 불필요) 판매일기준매출 = SUM(판매[매출금액]) -- 배송일 기준 (비활성 관계 → USERELATIONSHIP 필수) 배송일기준매출 = CALCULATE( SUM(판매[매출금액]), USERELATIONSHIP(판매[배송일], 날짜[Date]) )
두 측정값을 같은 보고서에 올려놓으면
날짜 슬라이서 클릭 시 → 판매일기준매출은 판매일로, 배송일기준매출은 배송일로 각각 필터링됨
⚠️ 핵심: 배송일 관계를 아예 만들지 않으면 USERELATIONSHIP도 사용 불가. 관계는 반드시 두 개 다 만들되, 하나는 활성·하나는 비활성으로 두는 것이 정석.

사용자가 어떤 필터를 선택하든 그 필터 기준으로 즉시 재계산. 보고서를 읽는 사람이 직접 분석 가능
2
필터를 무시하거나 덮어쓸 수 있음 (CALCULATE + ALL)
슬라이서로 강남구만 선택했어도 "서울 전체 합계"를 동시에 보여줄 수 있음 → 전체 대비 비율 계산 가능
3
여러 테이블을 넘나드는 집계
관계로 연결된 테이블들을 자동으로 참조해서 집계. 판매 테이블·제품 테이블·날짜 테이블을 동시에 참조하는 복잡한 계산도 수식 하나로 가능
4
시간 인텔리전스 — 전년 대비, 누계 자동 계산
SAMEPERIODLASTYEAR, TOTALYTD 같은 함수로 "작년 동기 대비 증감"을 슬라이서 연동 상태로 자동 계산. 엑셀에서는 수십 줄이 걸리는 작업
5
파일 용량을 늘리지 않음
계산 열은 테이블에 저장되어 파일 용량 증가. 측정값은 저장 안 되고 화면에 표시할 때만 계산 → 수백만 행 데이터도 빠르게 처리

DAX 개념 이해
What is DAX?
DAX란?
Data Analysis Expressions의 약자로, Analysis Services · Power BI · Excel 파워피벗에서 사용하는 수식 언어입니다.

DAX 수식은 테이블이나 열을 참조하여 계산식을 작성하며, 다양한 분석 함수·연산자·값이 포함됩니다.
-- 기본 구조 측정값명 = 함수명(테이블명[열이름])
DAX 구문
기본 구문 규칙
• 테이블 참조: 테이블명[열이름]
• 측정값 참조: [측정값명]
• 문자열: 큰따옴표 "텍스트"

📦 데이터 생태계 — Power BI 너머의 세계
Power BI는 데이터 시각화·분석 도구입니다. 하지만 실무에서는 데이터가 시각화 전에 수집 → 정제 → 가공 → 저장되는 데이터 파이프라인 전 과정이 먼저 필요합니다. 이를 담당하는 것이 데이터 엔지니어링입니다.

⚙️ ETL vs ELT 파이프라인
데이터 이동의 두 가지 방식
ETL (Extract → Transform → Load)
소스 추출 → 변환 먼저 → 저장. 전통적 방식. 온프레미스 환경.
ELT (Extract → Load → Transform)
소스 추출 → 저장 먼저 → 변환 나중에. 클라우드 환경의 주류. 빅데이터에 유리.
Power BI 파워쿼리는 소규모 ETL 역할. 대용량 자동화엔 Data Factory 같은 전용 도구 필요.

Data Factory + 웨어하우스 + Power BI 통합 플랫폼. Power BI Premium에 포함.
